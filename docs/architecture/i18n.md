# Internationalization & Regionalization Contract

## Launch locales

FounderOS launches with four product locales:

- `pt-BR` — Portuguese, Brazil (product default)
- `pt-PT` — Portuguese, Portugal
- `es-419` — Spanish, Latin America (LATAM master catalog)
- `en-US` — English, United States

Country-specific Spanish catalogs such as `es-MX`, `es-CO`, `es-AR`, `es-CL` and `es-PE` may be introduced later without changing domain contracts. Until then, browser tags `es-*` resolve to `es-419`.

## Locale is not geography

The product must never infer business geography from UI language. These fields are independent:

- `locale`
- `country`
- `currency`
- `timezone`
- `firstDayOfWeek`

Examples that must remain valid:

- `locale=en-US`, `country=BR`, `currency=BRL`, `timezone=America/Sao_Paulo`
- `locale=es-419`, `country=CO`, `currency=COP`, `timezone=America/Bogota`

`REGION_PRESETS` provides recommended launch defaults for BR, PT, MX, CO, AR, CL, PE and US. Presets are convenience data, not coupling rules.

## Precedence

Presentation locale is resolved in this order:

1. `founderos.locale` cookie (immediate UI switch)
2. authenticated user preference
3. organization regional preference
4. browser `Accept-Language`
5. `pt-BR` product default

For country, currency, timezone and first-day-of-week, user overrides take precedence over organization defaults, then product defaults.

## Persistence

Organization defaults live in `control_plane.regional_preferences`.
Human presentation overrides live in `control_plane.user_preferences` and are protected by self-only PostgreSQL RLS using `control_plane.current_actor_id()`.

Changing UI language does not silently mutate organization country or currency.

## Network boundary

`proxy.ts` is the trust boundary. It overwrites the following internal request headers before Server Components use them:

- `x-founder-locale`
- `x-founder-country`
- `x-founder-currency`
- `x-founder-timezone`
- `x-founder-first-day-of-week`

Client-supplied values with these names are not trusted.

## Formatting

User-facing numbers, money and dates must use helpers in `lib/i18n/format.ts` or `useI18n()`.
Do not add hard-coded `en-US` formatter calls in `app/`, `components/` or `lib/`.

A monetary value keeps its actual currency code. Locale controls presentation only. For example, USD data displayed under `pt-BR` remains USD but receives Brazilian formatting.

Timezones are validated as IANA timezone identifiers before a user preference is persisted.

## URL policy

Authenticated product URLs are not locale-prefixed at launch. Locale is a presentation preference carried by cookie/session. This prevents duplicated application routes such as `/pt-BR/agents` and `/es-419/agents` and keeps internal links stable.

A future public marketing site may use localized SEO routes independently of this application-shell policy.

## Catalog policy

Every new Axiom surface must ship all four translations in the same change. Catalog keys and named placeholders must have parity across all locales. `npm run i18n:verify` enforces this in CI.

Legacy screens are translated while they are rebuilt in the Axiom Design System, avoiding a throw-away translation pass over UI that is scheduled for replacement.

## `next-intl`

The product-facing i18n API is intentionally adapter-friendly. The current foundation uses native `Intl` plus our own typed catalog contract. `next-intl` can be placed behind this boundary once dependency installation is performed in a registry-enabled runner; domain code must not depend directly on a vendor-specific i18n API.
